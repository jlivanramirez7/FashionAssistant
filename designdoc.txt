FASHION ASSISTANT - DESIGN DOC
A phone web app that measures your body for clothing, hands-free.
Author: Ivan Ramirez
Last updated: 2026-10-10
Status: Draft - iterate with feedback

======================================================================
1. OVERVIEW
======================================================================
Fashion Assistant is a phone web app that measures a person for
clothing hands-free: the phone rests on the floor with its screen and
front camera facing the room, the user stands back and follows spoken
prompts, and the app reports body measurements with an uncertainty
for each.

Goal:
  A person alone at home gets a full set of clothing measurements in
  under 3 minutes, without a tape measure or a helper.

Users:
  One person measuring themselves on their own phone, any recent
  iPhone or Android, in a normal room. v1 is private: only the Google
  account jlivanramirez7@gmail.com can sign in (section 10).

Success criteria (v1):
  - Lengths (height, shoulder width, arm, inseam) within +/-1.5 cm of
    a tape measure for 80% of test users
  - Circumferences (chest, waist, hips) within +/-3 cm of a tape
    measure for 80% of test users
  - Accuracy is checked against tape measurements entered in
    validation mode (screen S9, section 6)
  - A full scan finishes in under 3 minutes, and fewer than 1 in 5
    scans need a retake
  - No images leave the device

Non-goals (v1):
  - Native apps
  - LiDAR or depth sensors
  - Measuring someone else. The one exception is validation scans of
    test people done on the owner's signed-in phone, labelled with
    subjectLabel (their own height is entered for that scan)
  - Virtual garment fitting
  - Size recommendation (moved to v2, with brand size charts and
    fit-ease rules); v1 shows measurements only

Key constraint: a single phone camera cannot tell how big something
is on its own. Most of this design is about getting a reliable
real-world scale, then turning flat 2D images into 3D measurements.

======================================================================
3. SCALE STRATEGY
======================================================================
The user's typed height is the primary scale source: it is the one
number most people know, and it is the only input we ask for. Every
other number the geometry needs (phone model, lens position, lens
height above the floor, focal length, tilt, camera resolution) is
pulled automatically from the device (device profile, section 4).
Floor geometry and an optional paper reference cross-check the
height and calibrate the camera.

Source              | How it gives scale             | Precision      | Role
--------------------|--------------------------------|----------------|-------------
User height (typed) | Head-to-heel distance in image | ~ +/-1 cm      | Primary
                    | equals known height            | (self-reported)|
Floor geometry      | Lens height (from L_lens and   | Noisy: camera  | Cross-check;
                    | tilt, section 4); the pixel    | sees feet at a | flags bad
                    | row where feet touch the floor | shallow angle  | captures
                    | gives distance to user         |                |
A4/Letter paper     | Known-size rectangle at the    | ~ +/-0.5 cm    | Optional;
on the floor        | user's feet                    |                | improves
                    |                                |                | focal length,
                    |                                |                | L_lens, k1

Because every measurement scales from height, the Setup screen shows
the tip: "Measure your height against a wall once - don't guess"
(people often round up 1-2 cm).

When the sources disagree by more than 2%, the app asks the user to
retake the scan or confirm their height.

======================================================================
4. CAMERA GEOMETRY
======================================================================
With lens height h and camera pitch phi known, every image point can
be converted into real-world coordinates on a vertical plane through
the user. This also removes the perspective distortion of looking up
from the floor ("giant legs, tiny head").

Side view (not to scale). The phone leans back against a wall or box
with its bottom edge on the floor; the screen and front lens face the
user, with the lens near the top of the phone:

  wall or box
     |
     |   o <- front lens (screen faces the user)
     |   |\ `-._   optical axis, raised phi above level
     |   | \     `-._
     |   |  \  phone   `-._                       O  head
     | h |   \ (L_lens)     `-._                 /|\
     |   |    \                                   |
     |   |     \ theta                           / \
  ---+---+------*------------ floor -------------+------
         <------------------ d ----------------->  feet
                bottom edge

Device profile (auto-detected, no user input):
  On the Start tap the app builds a device profile and feeds it into
  every calculation below. Nothing here is typed by the user.

  1. Phone model
     - Android Chrome: navigator.userAgentData
       .getHighEntropyValues(["model", "platformVersion"]) returns
       the exact model (e.g. "Pixel 8").
     - iOS Safari: the user agent only says "iPhone", so the model
       family is matched from screen.width x screen.height,
       devicePixelRatio and the iOS version. Phones in one family
       (same screen) have near-identical front-lens positions, so
       the family is enough.
     - If nothing matches, use the generic profile (below) and mark
       the scan lower confidence.
  2. Spec lookup: public/device-profiles.json, keyed by model or
     family, holds per phone:
       phoneHeightMm        body height
       frontLensFromTopMm   front lens centre to the top edge
       front35mmEqMm        front camera 35 mm-equivalent focal
                            length
       frontSensorAspect    e.g. "4:3"
     L_lens = phoneHeightMm - frontLensFromTopMm (stored as
     lensOffsetCm). Generic profile: L_lens 14 cm, 35 mm-eq 26 mm.
  3. Camera track: getSettings() gives the actual video width,
     height, frame rate and facing mode; getCapabilities() gives the
     maximum resolution.
  4. Focal length in pixels from the spec, for the actual video
     size (diagonal definition of 35 mm-equivalent, 43.27 mm):
       long  = max(W, H)
       short = long * sensor aspect (frontSensorAspect, default 4:3)
       f_px  = front35mmEqMm * sqrt(long^2 + short^2) / 43.27
     The 35 mm-equivalent is defined on the full sensor diagonal,
     and 16:9 video is a crop of the 4:3 sensor's long side; using
     the video's own diagonal would come out ~9% low. Any remaining
     crop error is corrected by the height solve (below).
  5. Sensors: DeviceMotionEvent accelerationIncludingGravity, sampled
     at ~60 Hz and averaged over each capture hold, gives tilt theta
     and roll (DeviceOrientationEvent beta/gamma as a fallback).
  6. Derived per scan: lens height h, pitch phi, f_px, and the
     distance d per view (formulas below).

  The profile is saved per device (users/{uid}/devices/{deviceId},
  section 11) with where each value came from (modelSource:
  "ua-client-hints" | "screen-match" | "generic"). Measured values
  from the height solve and the paper calibration override the spec
  values over time.

Angles:
  theta = phone tilt from flat, from the accelerometer gravity vector.
          Allowed range 60-85 deg.
  phi   = 90 deg - theta = camera pitch, the elevation of the optical
          axis above horizontal (5-30 deg).

Phone placement check:
  The gravity vector must show roll within +/-3 deg and tilt theta
  between 60 and 85 deg from flat before capture starts.

Lens height:
  h = L_lens * sin(theta)
  This is the camera's height above the floor. L_lens is the
  distance along the phone from its bottom edge to the front lens
  (~13-15 cm), taken from the device profile (above); theta comes
  from the gravity vector. Example: L_lens 14.0 cm, theta 75 deg ->
  h = 13.5 cm. A thick case adds a few mm; the paper calibration
  absorbs it. Stored per device as lensOffsetCm.

Distance from the feet:
  For image row v_feet (v increases downward), principal point c_y
  and focal length f_y (px):

    alpha = atan((v_feet - c_y) / f_y) - phi
    d     = h / tan(alpha)

  d is recomputed separately for each view (front, side, back) from
  that view's feet row, because the user moves slightly when turning.

  Feet row: the absolute row comes from the body outline's lowest
  edge near the feet (where the sole meets the floor). The heel and
  foot-index landmarks only give the offset from that lowest point to
  the floor point under the ankle (heel + 0.2 x (toe - heel)), so a
  shared error in landmark height cancels. In the side view the near
  foot's outer edge is ~0.025 x height closer than the body plane and
  is corrected for. This matters: with the lens ~13.5 cm up and the
  user 2.5 m away, 1 cm of error at the feet moves d by ~18 cm.

  If d cannot be determined (feet ray at or above the horizon, h <= 0
  or d > 50 m), distanceFromFeet returns 0 as an "invalid" marker;
  the view plane then falls back to the typed height alone and
  flags the view for retake.

Head-top correction:
  From a camera near the floor, the top of the head outline sits
  slightly above the true crown (the skull is a rounded 3D shape
  seen from below). The view plane subtracts sqrt(c^2 + T^2 b^2) - c
  using head semi-axes of 0.066 H (tall), 0.057 H (front-back) and
  0.043 H (side-to-side), H = typed height. Without it, height reads
  ~1% high.

Perspective correction:
  Each landmark's pixel ray is rotated by the pitch phi into a level
  frame and intersected with the vertical plane at that view's
  distance d, then scaled by height. That gives metric (x, y) for
  every landmark, so lengths are in centimetres, not pixels. Levels
  are matched across views by height above the floor (cm).

Lens distortion:
  Front cameras are often wide-angle. Model one radial coefficient
  k1, estimated during the optional paper calibration and stored per
  device (distortionK1). Without it: require the whole body inside
  the central ~80% of the frame and add the expected distortion error
  to each measurement's uncertainty.

Focal length:
  Browsers don't expose it directly. The starting value comes from
  the device profile (f_px from the 35 mm-equivalent spec). Each scan
  then checks it: with user height H and pitch phi, the head ray and
  feet ray must both hit the same vertical plane; solve that
  constraint for f_y. If the solved value differs from the spec value
  by more than 5%, the solved value wins (the video mode is probably
  cropped). Save the result per device and refine it across scans or
  with the paper reference.

======================================================================
5. CAPTURE FLOW (state machine with voice prompts)
======================================================================
The user will be 2-3 m from the screen, so every instruction is
spoken (speechSynthesis) and shown in large text. Capture happens
automatically when the pose holds still, so the user never has to
walk back to tap anything. The preview is mirrored for the user, so
turn prompts never say "turn right/left".

Live guidance runs pose_landmarker_lite on every frame (no
segmentation). On capture, ~10 full-resolution frames per step are
kept in memory; heavy processing waits until all steps are done.

  1. Setup (S3): enter height (required) and body type (optional:
     male / female / unspecified, stored as bodyType). bodyType
     labels chest vs bust on Results and picks per-body-type
     correction factors. Tip: "Measure your height against a wall
     once - don't guess". Checklist: fitted clothes, hair tied up,
     plain wall, good light.
  2. Start tap: grants camera and motion permission and unlocks
     voice in one gesture, then silently builds the device profile
     (phone model, lens offset, focal length, camera resolution;
     section 4). No questions are asked.
  3. Place the phone: lean it against a wall or box on the floor,
     screen and front camera facing the room. A live level gauge
     turns green when tilt and roll are in range.
  4. Position the user: "Step back... stop." Wait until the whole
     body is in frame and feet are visible on the floor (ankles and
     nose landmarks in frame, body ~70% of frame height, inside the
     central ~80% of the frame for nose, shoulders, hips and ankles;
     wrists only need to stay inside the frame, because an A-pose at
     70% of frame height puts them near the edges).
  5. Step 1 of 3 - Front A-pose: arms ~45 deg out from the body,
     palms forward, feet hip-width apart. Hold ~1 s (~10 frames).
     Sleeve and shirt-sleeve come from this pose (arm segment
     lengths do not depend on the arm angle).
  6. Step 2 of 3 - Side: "Turn so your right shoulder faces the
     phone." Arms relaxed at the sides. Hold ~1 s.
  7. Step 3 of 3 - Back A-pose: "Turn so your back faces the
     phone." Arms ~45 deg out. Hold ~1 s. Required (shoulder width,
     back length).
  8. Processing (S6): pose_landmarker_heavy + crop segmentation run
     on the kept frames (section 7), ~5-15 s on a mid-range phone,
     with a progress bar.
  9. Quality check: confidence per measurement. Re-capture only the
     step whose frames are blurry, partly out of frame, or whose
     distance disagrees with the floor-geometry estimate.
 10. Results (S7): measurements with a +/- uncertainty each, and
     Copy all. No size recommendation in v1 (v2).

There is no T-pose step (arm span does not fit a portrait frame). An
optional slow 360 deg spin for a better circumference fit moves to v2.

The screens for each step are in section 6.

6. USER INTERFACE
======================================================================
The UI is deliberately minimal: one job per screen, one big button,
and nothing to tap once capture starts. It walks the user through
three things: set up the phone, record the scan, read the
measurements.

Design rules:
  - One primary action per screen, as a large full-width button at
    the bottom (thumb reach)
  - The FRONT (selfie) camera is used (getUserMedia facingMode
    "user"), so the screen faces the user standing 2-3 m away. The
    on-screen preview is mirrored like a mirror; all computation
    uses the unmirrored frames
  - During capture the user is 2-3 m away: instruction text is huge
    (at least 48 px, about 6 words max), high contrast, and every
    instruction is also spoken as a full sentence
  - Turn instructions never say "turn right/left" (ambiguous with a
    mirrored preview); they name the body part that faces the
    phone, e.g. "Turn so your right shoulder faces the phone"
  - A coloured border around the camera view gives status from
    across the room: red = not ready, amber = hold still,
    green = capturing
  - Screen stays awake during setup and capture (Screen Wake Lock
    API); app runs full screen in portrait
  - The camera runs as live video and frames are analysed on the
    fly; nothing is recorded to storage or uploaded (the only
    exception is the dev-only Debug capture, see S3)
  - Units: inches by default with a cm toggle (saved per user)

Screen flow:

            [History] <------ [Results] <------ [Processing]

======================================================================
7. MEASUREMENT PIPELINE
======================================================================
Lengths come from scaled pose landmarks (~ +/-1-2 cm). Circumferences
come from front and side outlines and are harder (~ +/-2-4 cm).

Pipeline steps (run in the Processing step, after all 3 captures):
  1. Capture frames: ~10 full-resolution frames per step (Front
     A-pose, Side, Back A-pose), kept in memory only.
  2. Heavy pose: run pose_landmarker_heavy on every captured frame.
  3. Perspective correction per view, each with its own distance d
     from that view's feet row, scaled by height (see "Aligning
     views").
  4. Region crops + segmentation + edge refinement (see
     "Segmentation resolution").
  5. Locate body levels (see "Body level definitions").
  6. Measure widths (front/back) and depths (side) at each level,
     plus landmark lengths.
  7. Ellipse circumference at each level.
  8. Apply correction factor k (per body level and bodyType).
  9. Average over frames (drop outliers) and report uncertainty =
     frame spread + lens-distortion error when the device has no
     distortionK1 (section 4).

The app reports the standard measurements that size charts ask for,
grouped by garment type as on the Results screen (section 6).

Views are the 3 capture steps only: Front (A-pose), Side, Back
(A-pose). There is no T-pose: sleeve and shirt sleeve come from the
front A-pose, because arm segment lengths do not depend on the arm
angle. Shoulder width and back length use the back view, which is
required.

Chest and bust are the same measurement at the same body level; the
Results screen labels it by the bodyType chosen in Setup: "Bust"
(female), "Chest" (male), "Chest / bust" (unspecified).

Body level definitions:
  All heights are in cm above the floor, in the perspective-corrected
  metric plane. Front width and side depth are taken at the SAME
  height.
  - Neck: narrowest neck width between shoulder line and mouth
    landmarks (front).
  - Shoulder point: outline edge at shoulder-landmark height
    (front/back).
  - Armpit: where the arm outline separates from the torso in the
    front A-pose.
  - Chest/bust: greatest torso depth in the side view between armpit
    and natural waist.
  - Underbust: narrowest side-view depth just below the bust level
    (upper half of bust-to-waist span).
  - Natural waist: narrowest front torso width between chest and hip
    landmarks.
  - Pant waist (belt line): hip-landmark height + 40% of the distance
    up to the natural waist (tuned with validation data).
  - Hips/seat: greatest side-view depth between hip landmarks and
    crotch.
  - Crotch: top of the gap between the legs in the front A-pose mask.
  - Thigh: 5 cm below crotch. Knee: knee landmark. Calf: widest
    lower-leg width between knee and ankle. Bicep: widest point
    between shoulder and elbow. Wrist: wrist landmark.
  - Nape (back length start): base of neck in side/back view at
    shoulder-landmark top.

Segmentation resolution:
  The segmenter outputs a 256x256 mask. Run over the whole frame, one
  mask pixel covers ~1 cm of body, so a width or depth is off by up
  to ~2 cm before any other error - too coarse for +/-2-3 cm
  circumference targets. Instead:
  - Pose landmarks -> padded crop boxes per region (neck/shoulders,
    torso, each arm, each leg), cut from the full-resolution frame.
  - Run ImageSegmenter (selfie_multiclass_256x256) on each crop, so a
    ~40 cm region gets ~1.5-2 mm per mask pixel.
  - Edge refinement: snap the mask boundary to the strongest image
    gradient along the outline normal within +/-3 px.
  - In M3 also evaluate PoseLandmarker's own segmentation mask
    (outputSegmentationMasks, full-body trained) as an alternative;
    keep whichever validates better.

Aligning views:
  Each view (front, side, back) is perspective-corrected separately
  with its own distance d recomputed from its feet row (the user moves
  slightly when turning) and scaled by height. Levels are matched
  across views by height above the floor (cm), not by pixel row.

Circumference method:
  At each body level, the front outline gives width w and the side
  outline gives depth d. Model the cross-section as an ellipse with
  a = w/2, b = d/2, using Ramanujan's approximation:

    C ~= k * pi * [ 3(a + b) - sqrt((3a + b)(a + 3b)) ]

  k is a correction factor per body level and bodyType (torsos are
  not true ellipses).

Correction factors:
  k is computed from validation data (screen S9 Validation, section
  6): k = mean(tape / raw ellipse estimate) per body level and
  bodyType, shown in the "Validation summary" view. Factors are
  stored in users/{uid}/settings/correctionFactors as
  { male: {key: k}, female: {...}, unspecified: {...}, updatedAt }.
  Until enough validation scans exist, k defaults to 1.0. Each scan
  keeps its uncorrected values in rawMeasurements, so k can be
  recomputed and past scans re-corrected at any time.

Noise handling:
  Each pose is captured over ~10 frames. Average after dropping
  outliers; keep the spread as the reported uncertainty, and add the
  expected lens-distortion error when the device has no distortionK1.
  Loose clothing pushes values up, so the "fitted clothing"
  instruction matters a lot.

Performance:
  Live guidance runs pose_landmarker_lite every frame (no
  segmentation). The heavy model and crop segmentation run only in the
  Processing step on the ~10 kept frames per step. Processing takes
  ~5-15 s on a mid-range phone, with a progress indicator.

v2 upgrade:
  Fit a parametric body model (SMPL-X) to the landmarks and outlines
  from every view, then measure the fitted 3D mesh. This is how
  commercial apps (3DLOOK, Bodygram) work. More accurate for
  circumferences but heavier, probably server-side. v2 also adds an
  optional 360-deg spin capture and size recommendation: brand size
  charts plus fit-ease rules map measurements to a size per brand.
  v1 shows measurements only.

10. AUTHENTICATION AND ACCESS CONTROL
======================================================================
Users sign in with Google (Firebase Authentication). Only the Google
account jlivanramirez7@gmail.com can use the app. The allowlist is
enforced in two places:

  1. Server side (the real protection): Firestore security rules
     reject every read and write unless the signed-in token's email
     is jlivanramirez7@gmail.com, the email is verified, and the
     sign-in provider is Google. See section 11.
  2. Client side (user experience only): after sign-in the app
     checks the email; any other account is signed out immediately
     and shown "This app is private."

Sign-in flow:
  1. App loads -> getRedirectResult() finishes a pending redirect
     sign-in (if any); onAuthStateChanged() checks for a session.
  2. No session -> show a "Sign in with Google" button.
  3. Tap -> GoogleAuthProvider with login_hint =
     jlivanramirez7@gmail.com, then:
       Production: signInWithRedirect(); the page goes to the
       same-origin helper https://<app-host>/__/auth/handler and
       comes back to the app, which handles getRedirectResult().
       Dev: signInWithPopup().
  4. Email != allowed email -> signOut(), show the "private" message.
  5. Allowed -> session persists on the phone (local persistence is
     the default), so later visits skip sign-in; continue to Home.
  6. A "Sign out" link lives on the Home screen (S2).

Why redirect with a same-origin helper: popup sign-in often fails in
an installed iOS home-screen app (PWA). Plain signInWithRedirect is
also unreliable when the app's domain (run.app) differs from the auth
domain (firebaseapp.com), because Safari and Chrome block third-party
storage. Serving the auth helper from the app's own origin fixes
that:
  - nginx proxies /__/auth/ and /__/firebase/ to
    https://fashionassitant.firebaseapp.com (proxy_pass,
    proxy_ssl_server_name on, Host header set to the firebaseapp
    host; section 12).
  - VITE_FIREBASE_AUTH_DOMAIN = the app's own host (run.app host or
    custom domain) in .env.production. In .env.development it stays
    fashionassitant.firebaseapp.com and dev uses signInWithPopup.
  - The code picks redirect when authDomain equals location.host,
    otherwise popup.

Firebase Auth settings (console):
  - Sign-in method: enable Google only; support email
    jlivanramirez7@gmail.com
  - Authorized domains: localhost, the Cloud Run run.app host (and
    custom domain, if mapped), and any dev host used for phone
    testing (section 13)
  - OAuth redirect URI: add https://<app-host>/__/auth/handler to
    the OAuth 2.0 Web client's authorized redirect URIs (Google
    Cloud console > APIs & Services > Credentials).
  - The run.app host is only known after the first deploy: deploy
    once, set VITE_FIREBASE_AUTH_DOMAIN + redirect URI, redeploy.

Hardening:
  - Restrict the Firebase browser API key (Google Cloud console >
    APIs & Services > Credentials) to HTTP referrers: the run.app URL,
    https://fashionassitant.firebaseapp.com (dev popup) and localhost
    (section 13, step 14).
  - Do not set the response header
    Cross-Origin-Opener-Policy: same-origin; it breaks the dev
    sign-in popup.
  - Other Google accounts can still complete Google sign-in and get
    an (empty) Firebase Auth user record, but they can read and
    write nothing. Optional later: block them at sign-in with an
    Identity Platform blocking function.

Code sketch - src/auth/authGuard.ts:

  import { GoogleAuthProvider, getRedirectResult, onAuthStateChanged,
           signInWithPopup, signInWithRedirect, signOut,
           type User } from "firebase/auth";
  import { auth } from "./firebase";
  import { ALLOWED_EMAIL, firebaseConfig } from "../config";

  // Production: authDomain is the app's own host (same-origin
  // helper via nginx) -> redirect. Dev: firebaseapp.com -> popup.
  const useRedirect = firebaseConfig.authDomain === location.host;

  export function isAllowed(user: User | null): boolean {
    return !!user && user.emailVerified &&
           user.email?.toLowerCase() === ALLOWED_EMAIL;
  }

  async function checkAllowed(user: User | null): Promise<void> {
    if (user && !isAllowed(user)) {
      await signOut(auth);
      throw new Error("This app is private.");
    }
  }

  // Call once on load, before showing the sign-in screen.
  export async function finishRedirect(): Promise<void> {
    const result = await getRedirectResult(auth);
    await checkAllowed(result?.user ?? null);
  }

  export async function signIn(): Promise<void> {
    const provider = new GoogleAuthProvider();
    provider.setCustomParameters({ login_hint: ALLOWED_EMAIL });
    if (useRedirect) {
      await signInWithRedirect(auth, provider); // page navigates away
      return;
    }
    const { user } = await signInWithPopup(auth, provider);
    await checkAllowed(user);
  }

  export function watchAuth(onChange: (u: User | null) => void) {
    return onAuthStateChanged(auth, async (user) => {
      if (user && !isAllowed(user)) { await signOut(auth); user = null; }
      onChange(user);
    });
  }

firestore.rules:

  rules_version = '2';
  service cloud.firestore {
    match /databases/{database}/documents {
      function isAllowedUser() {
        return request.auth != null
          && request.auth.token.email == 'jlivanramirez7@gmail.com'
          && request.auth.token.email_verified == true
          && request.auth.token.firebase.sign_in_provider == 'google.com';
      }
      match /users/{uid}/{document=**} {
        allow read, write: if isAllowedUser() && request.auth.uid == uid;
      }
      // Everything else is denied by default.
    }
  }

With rules_version 2, {document=**} matches zero or more segments,
so this one rule covers users/{uid} itself and every subcollection
(scans, devices, settings). The new collections need no rule changes.

"Delete all my data" (History, section 6) works client-side under
these rules: the web SDK cannot delete a subtree in one call, so the
app lists users/{uid}/scans, devices and settings, deletes those
documents in batched writes (max 500 per batch), deletes users/{uid},
then calls terminate() + clearIndexedDbPersistence() to clear the
local Firestore cache and removes the stored deviceId from
localStorage.

Rules are deployed with the Firebase CLI (section 13) and should be
tested with the Firestore emulator: the allowed account can
read/write its own subtree; any other account and anonymous requests
are denied.

nginx.conf (the project ID fashionassitant is typed in directly; it
is a public identifier):

  server {
    listen 8080;
    root /usr/share/nginx/html;
    gzip on;
    gzip_types text/css application/javascript application/json
               application/wasm;
    location / {
      try_files $uri $uri/ /index.html;
    }
    location = /sw.js {
      add_header Cache-Control "no-cache";
    }
    location /assets/ {
      add_header Cache-Control "public, max-age=31536000, immutable";
    }
    # Same-origin Firebase Auth helper for signInWithRedirect
    # (section 10)
    location /__/auth/ {
      proxy_pass https://fashionassitant.firebaseapp.com;
      proxy_ssl_server_name on;
      proxy_set_header Host fashionassitant.firebaseapp.com;
    }
    location /__/firebase/ {
      proxy_pass https://fashionassitant.firebaseapp.com;
      proxy_ssl_server_name on;
      proxy_set_header Host fashionassitant.firebaseapp.com;
    }
  }

  The /__/ prefix locations are longer than "/", so nginx uses them
  instead of the index.html fallback. Do not add a
  Cross-Origin-Opener-Policy: same-origin header (it breaks the dev
  popup).

15. RISKS AND OPEN QUESTIONS
======================================================================
The biggest risk is circumference accuracy; the biggest open decision
is whether v1 stays fully on-device for image processing.

Risks:
  - Circumferences miss the +/-3 cm target -> wrong size.
    Mitigation: tape-measure validation early (M3, validation
    mode); per-level, per-bodyType correction factors; v2
    body-model fit.
  - Coarse segmentation (256x256 mask) -> outline edges off by
    several mm to cm.
    Mitigation: per-region crops at full resolution (~1.5-2 mm per
    mask pixel) plus edge refinement to the strongest image
    gradient; compare with PoseLandmarker's mask in M3.
  - Loose clothing inflates outlines -> chest/waist/hips too large.
    Mitigation: clear "fitted clothing" instruction; detect loose
    outlines and warn.
  - Floor-level view hides face or shoulders for some body types ->
    missing landmarks.
    Mitigation: step further back (up to 3 m) or tilt the phone
    within the 60-85 deg range; the lens-height formula assumes
    the phone's bottom edge is on the floor, so no chair.
  - Busy background or clothing the same colour as the wall ->
    segmentation fails.
    Mitigation: quality check on the outline; ask the user to move.
  - Front-camera lens distortion (often wide-angle) -> widths near
    the frame edges are stretched.
    Mitigation: radial coefficient distortionK1 from the paper
    calibration; without it, keep the whole body inside the
    central ~80% of the frame and add the expected distortion
    error to each measurement's uncertainty.
  - Self-reported height is often rounded up 1-2 cm -> every
    measurement scales by the same error.
    Mitigation: Setup tip "Measure your height against a wall once
    - don't guess"; floor-geometry cross-check (scaleAgreementPct).
  - Phone model not detected or not in device-profiles.json (iOS
    only exposes "iPhone"; new models ship every year) -> lens
    height and focal length start from generic values.
    Mitigation: iOS screen-size match picks the model family; the
    generic profile (L_lens 14 cm, 26 mm-eq) lowers confidence;
    the height solve corrects focal length on every scan; paper
    calibration stores lensOffsetCm per device; add new models to
    the JSON as they appear.
  - Spec focal length wrong for the video mode (some phones crop
    the sensor for video) -> perspective correction off.
    Mitigation: the height solve overrides the spec value when they
    differ by more than 5%; the result is saved per device.
  - Unknown focal length per phone -> perspective correction off.
    Mitigation: solve from user height and tilt; save per device.
  - Processing is slow or the phone heats up on mid-range phones
    (heavy pose model + crop segmentation on ~10 full-res frames
    per step).
    Mitigation: lite model only for live guidance; heavy model and
    segmentation only in the Processing step (~5-15 s, with
    progress); record processingMs in diagnostics.
  - iOS browser limits (permissions, camera stops in background) ->
    scan breaks midway.
    Mitigation: unlock everything on the Start tap; resume from the
    last completed pose.
  - Sign-in fails in the installed iOS home-screen app (popups are
    unreliable there).
    Mitigation: signInWithRedirect with the same-origin /__/auth/
    helper proxied by nginx; no COOP same-origin header (breaks the
    dev popup); test the installed iOS app and Android Chrome in
    M0.
  - Large MediaPipe models slow the first load on mobile data.
    Mitigation: service-worker cache after first load; show a
    download progress bar.

Open questions:
  [ ] Keep image processing fully on-device, or allow optional
      upload for a more accurate server-side fit (v2)?
  [ ] Which measurements matter most to you (tops, trousers,
      tailoring)?
  [ ] Which phones do we test on first?
  [ ] Which iPhone and Android models go into device-profiles.json
      first? (Start with the phones you will test on.)
  [ ] Region: keep us-central1 or pick one closer to you?
  [ ] Custom domain, or is the run.app URL fine?
